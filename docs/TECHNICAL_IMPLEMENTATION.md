[返回 README](../README.md) · [GitHub 仓库](https://github.com/xyxiao001/kingdomRush)

本文分析当前仓库的实际实现，重点解释一场战斗如何从资源加载走到画面呈现，以及移动、攻击、技能、存档等细节如何协作。文中的简化代码和公式用于解释流程，不是可以直接替换源码的实现。

## 1. 代码如何分工

游戏主体位于 `apps/kr1`，共享能力放在 `packages`。共享包提供基础函数和浏览器组件，具体的一代战斗规则仍主要由应用层实现。

| 层次 | 主要入口 | 负责内容 |
| --- | --- | --- |
| 启动 | [bootstrap.ts](../apps/kr1/src/bootstrap.ts) | 加载界面、PWA 初始化、存档选择、动态导入主程序 |
| 应用编排 | [main.ts](../apps/kr1/src/main.ts) | 地图与战斗切换、输入、主循环、事件消费、通关保存 |
| 内容定义 | [levels/index.ts](../apps/kr1/src/levels/index.ts)、[content/types.ts](../apps/kr1/src/content/types.ts) | 关卡结构、路线、波次、防御塔与战斗数据类型 |
| 战斗模拟 | [simulation/battle.ts](../apps/kr1/src/simulation/battle.ts) | 实体状态、移动、选敌、攻击、伤害、胜负 |
| 特殊行为 | [simulation](../apps/kr1/src/simulation)、[levels/scripts](../apps/kr1/src/levels/scripts) | 英雄技能、敌人能力、刷怪、无尽与关卡脚本 |
| 渲染 | [rendering/scene.ts](../apps/kr1/src/rendering/scene.ts) | Pixi 场景、纹理、精灵、血条、绘制与坐标转换 |
| 浏览器组件 | [packages/game-web/src](../packages/game-web/src) | 相机、界面树、菜单、字体、PWA 客户端 |
| 资源与声音 | [asset-runtime](../packages/asset-runtime/src)、[audio](../packages/audio/src) | 资源进度、Service Worker、音频解码和播放 |
| 持久化 | [storage](../apps/kr1/src/storage)、[game-storage](../packages/game-storage/src) | 存档槽、设置、关卡星星、成就和记录 |

一次操作的典型方向是：输入处理将屏幕坐标转换为战场坐标，调用 `Battle` 的动作方法；模拟更新状态并写入事件；主程序消费事件，渲染层读取状态更新画面。

例如建塔时，金币扣除和塔状态创建发生在模拟层。界面根据操作结果关闭菜单或显示反馈，随后渲染层绘制建造过程。金币不会由按钮动画自行扣除。

## 2. 从打开页面到进入战场

### 2.1 启动阶段

`bootstrap.ts` 先配置资源体积清单，再处理 PWA 初始化和存档选择，最后动态导入 `main.ts`，等待它导出的 `ready`。标题和存档选择使用浏览器界面，地图与战斗主体使用 Pixi 场景。

这样的顺序将启动页面与完整游戏初始化分开。用户选好存档后，游戏中的进度读取才对应当前存档槽。

### 2.2 按场景加载

进入游戏先准备地图相关字体、纹理和声音。进入战场时，`startBattle` 再加载选中关卡与英雄的内容，并准备通用战斗资源、关卡资源和相应音频。

关卡目录只携带选择地图需要的摘要。完整关卡通过 `loadLevel(id)` 从以下地址读取：

```text
/assets/kr1/levels/NN/content.json
```

英雄内容通过 [content/heroes.ts](../apps/kr1/src/content/heroes.ts) 的 `loadHero(id)` 读取：

```text
/assets/kr1/heroes/<hero-id>/content.json
```

关卡和英雄加载函数分别用 `Map<id, Promise<内容>>` 保存加载任务；通用战斗资源也复用加载 Promise。同一页面会话内再次进入已经加载过的场景时，可以复用结果。这里的复用不等同于持久离线缓存，后者由 Service Worker 管理。

选定挑战模式后，主程序将模式配置合入关卡数据，再创建 `Battle`，传入种子、难度、模式、星星升级与英雄内容。

### 2.3 进度条怎样计算

[ResourceLoader](../packages/asset-runtime/src/progress.ts) 将每个资源分成四个阶段：

| 阶段 | 含义 |
| --- | --- |
| `queued` | 已进入当前加载阶段，尚未开始读取 |
| `reading` | 正在读取响应流并累计字节 |
| `processing` | 字节读取结束，解析或解码尚未宣布完成 |
| `ready` | JSON 解析、纹理解码或音频解码等工作完成 |

总大小来自构建生成的资源清单，已读取大小来自 `ReadableStream`。因此“字节读完”与“资源可以使用”是两个状态：大图或音频还需要解码。

这份统计衡量应用读取的数据，不是浏览器网络面板里的实际网络流量；命中浏览器缓存或 Service Worker 缓存的响应同样可以被读取和计数。

资源地址也分两步处理：[resource-url.ts](../apps/kr1/src/loading/resource-url.ts) 将 `/assets/` 前缀接到配置的应用基础路径下；[asset-url.ts](../apps/kr1/src/rendering/asset-url.ts) 查找生成的资源映射，选择实际图片文件。图片格式由映射确定，没有运行时逐个尝试格式的流程。

## 3. 时间、固定步长与事件

### 3.1 模拟时间与表现时间

[balance.ts](../apps/kr1/src/content/balance.ts) 定义 `STEP = 1 / 60`。主循环通过 `requestAnimationFrame` 得到真实帧间隔，再用累加器推进模拟。简化流程如下：

```ts
presentationTime += elapsed;
if (正在战斗 && 未暂停 && 未结束) {
  accumulator += elapsed * gameSpeed;
  while (accumulator >= STEP) {
    battle.step();
    accumulator -= STEP;
  }
}
update();
scene.render();
```

屏幕刷新率只影响每次绘制之间推进多少个模拟步。正常情况下，移动使用 `速度 × STEP`，攻击判断使用战斗时间，避免把游戏速度直接绑定到屏幕帧数。

`presentationTime` 独立累加，菜单、提示和结算动画可以在战斗暂停后继续播放。战斗暂停则不推进 `Battle.time`，依赖它的冷却、移动与持续效果一起停止。

固定步长是 60 Hz，许多动画和前摇数据仍按 30 帧换算。例如 `6 / 30` 表示 0.2 秒，而不是六个模拟步；序列帧动画也通过 `floor(age * 30)` 取帧。

### 3.2 每一步的更新顺序

`Battle.step()` 在暂停或结束时直接返回，其余情况先推进时间。主要顺序为：

1. 场景道具、波次、定点刷怪、隧道乘客与延迟声音。
2. 敌人能力管理、无尽机制、防御塔、士兵、英雄。
3. 敌人行动、关卡刷怪和剧情脚本。
4. 连锁效果、孵化物、特殊刷怪源、射线与投射物。
5. 持续燃烧、过期效果和敌人清理，最后判断胜负。

顺序会影响同一帧的结果。例如塔在这一模拟步释放投射物，投射物会在后面的阶段得到处理；死亡触发的刷怪队列也要参与最终胜负判断。阅读某项能力时，应同时查看它在主循环里的位置。

### 3.3 事件怎样传到界面

模拟层把 `sound`、`seen`、`achievement`、`victory` 等事件放入 `battle.events`。主程序通过 `splice(0)` 取出事件并处理声音、百科解锁、成就通知和战斗反馈。

这让规则层记录“发生了什么”，主程序负责“如何反馈给玩家”。但当前项目并非全部使用事件驱动：画面、血条和 HUD 仍会读取战斗状态，`main.ts` 也承担较多界面编排工作。

### 3.4 随机数与可复现范围

战斗使用带种子的线性同余随机数生成器：

```text
seed = (seed × 1664525 + 1013904223) mod 2^32
random = seed / 2^32
```

实现通过 `Math.imul` 和无符号位运算保留 32 位行为；应用创建战斗时传入 `12345`。路线分支、伤害区间与部分能力概率消费这条随机序列。装饰物使用另一条 `propSeed` 序列，避免装饰动画消耗战斗随机数。

固定种子有助于复现，但完整过程仍取决于输入落在哪个模拟步，以及调用顺序。音效选择、部分提示等表现代码还会使用 `Math.random`，仓库也没有完整的输入录像回放系统。

## 4. 关卡、波次与结束判定

### 4.1 数据与逻辑共同描述关卡

[LevelContent](../apps/kr1/src/levels/index.ts) 不只描述背景图，还包含路径、路线分组、导航网格、建塔位置、资源包、UI、模式配置和特殊机制数据。常规差异由数据表达，复杂关卡行为由专门脚本执行。

战役运行时读取已经组织好的 `wave.spawns`，每条刷怪记录包含相对时间、敌人类型、路线与可选分支。不要把共享包中的所有工具都当成战役必经流程；直接追踪 `Battle.updateWaves()` 才能看到当前运行入口。

### 4.2 波次不是一次性生成所有敌人

`updateWaves()` 比较 `Battle.time - waveStarted` 与下一条刷怪记录的时间，用循环消费当前已到期的记录。没有指定分支时，才使用战斗随机数从对应路线的分支中选择。

当前波次的刷怪记录全部消费后，才记录 `waveFinishedAt`。下一波倒计时基于这个时刻，场上仍可存在上一波敌人。因此提前召唤会让不同波次同时存在于战场。

提前召唤奖励由剩余倒计时和模式系数计算，并影响金币与技能冷却；主程序根据调用结果显示金币和冷却时间反馈。倒计时 UI 不自行修改战斗数值。

### 4.3 为什么没有活敌人也可能尚未胜利

胜利要求最后一波结束，并且场上没有活敌人，同时等待后续敌人来源清空，包括定点刷怪、死亡衍生单位、隧道乘客、孵化物、墓地队列与关卡脚本待办。Boss 还可能要求等待死亡演出时间。

如果只看 `enemies.length === 0`，隧道里的敌人或正在孵化的单位就可能被漏掉。当前代码把这些队列直接纳入判定。

战役星级按剩余生命决定：至少 18 点为三星，至少 6 点为二星，其余胜利为一星。英雄挑战与钢铁挑战通过各自进度字段记录完成难度；无尽模式不走普通战役胜利条件。

## 5. 敌人路线与英雄寻路

### 5.1 敌人沿折线路径移动

`Battle` 初始化时为路径计算每段累计长度。敌人保存 `lane` 和 `distance`，每步增加前进距离，再找出所在路径段，在两个节点间线性插值得到位置：

```text
distance += effectiveSpeed × STEP
t = (distance - cumulative[i-1]) / (cumulative[i] - cumulative[i-1])
position = points[i-1] + (points[i] - points[i-1]) × t
```

减速、束缚、阻挡、施法、出生动作等状态会影响是否移动及有效速度。敌人的朝向来自当前路径段方向，供行动和显示使用。

塔常用的优先级是 `remainingDistance()`，即距出口还有多远。存在隧道时，这个函数会组合入口前剩余路程与出口后的路程，避免只比较当前路径数组的长度。

进入隧道后，敌人移入 `tunnelPassengers`，根据距离、速度和隧道系数计算释放时间；到时放回出口路径。期间它不会作为普通场上敌人参与目标选择，胜负判断仍会等待它。

### 5.2 英雄使用网格 A*

英雄需要响应玩家指定的位置，使用 [hero-navigation.ts](../apps/kr1/src/simulation/hero-navigation.ts) 和共享的 [gridWaypoints](../packages/engine/src/pathfinding.ts)。

当前寻路细节如下：

- 网格单元大小为 16，地形值通过位掩码判断能否通行。
- 搜索八个方向，直线代价为 1，对角代价为 1.4142，启发值为到终点的欧氏距离。
- 开放节点保存在普通数组中，每轮线性选出评分最低的节点；前驱与累计代价使用 `Map`。
- 返回网格路径时去掉首个中间格；存在返回路点时，将最后一个路点替换为精确目标位置。

英雄被近战带到不可走区域时，现有实现会尝试从集结点所在网格开始，再在附近最多五格范围寻找可用起点。玩家点击位置不合适时，`heroRally` 还会沿点击点到英雄的方向取样，尝试找到符合条件且可寻路的位置。

因此，英雄最终落点可能与原始点击略有差异。它由地形、道路宽度和寻路结果共同决定，不是直接把英雄坐标设置为鼠标位置。

### 5.3 施法区域另有规则

英雄移动、兵营集结和技能施放不是同一种可达性判断。火雨等目标选择还会参考地形位、道路宽度及关卡配置的可施法区域。画面上看起来是空地，并不必然意味着所有指令都能在该处生效。

## 6. 防御塔、伤害与弹道

### 6.1 一次普通攻击的生命周期

以普通防御塔为例，攻击流程分成以下阶段：

1. 过滤活着、未逃脱、可被攻击且符合地面或飞行限制的敌人。
2. 检查射程，通常按距离出口的剩余路程排序。
3. 冷却结束后记录目标和攻击动作，设置前摇结束的 `releaseAt`。
4. 到释放时刻，再查找目标状态并按塔类型生成投射物或效果。
5. 投射物到达或伤害时刻到期后，进入伤害结算。

毒箭等能力会增加自己的排序条件；高级塔由专门处理函数实现，不能用一条普通攻击公式概括。建塔也有独立建造时间，兵营还维护士兵数量、复活时间与开关门动作。

`readyAt`、`releaseAt` 等时间字段把“可以开始攻击”和“实际出手”分开。近战类似地分离 `attackAt`、`hitAt` 与动作开始时间，使伤害落在攻击动作的指定时刻。

### 6.2 射程为什么是椭圆

核心范围判断使用 `ASPECT = 0.7`：

```text
(target.x - origin.x)^2 + ((target.y - origin.y) / 0.7)^2 <= range^2
```

同样的世界范围在画面纵向被压缩，符合俯视战场的表现。许多范围攻击也使用这个函数；用于路径长度或两点移动的普通距离则仍是欧氏距离。分析技能范围时，需要区分这两种距离。

### 6.3 不同伤害类型如何处理护甲

[battle.ts](../apps/kr1/src/simulation/battle.ts) 的 `damageAfterArmor` 选择抗性，共享的 [damageAfterResistance](../packages/engine/src/damage.ts) 完成乘法与向下取整。

| 伤害类型 | 基础抗性选择 |
| --- | --- |
| `physical` | 物理护甲 |
| `shot` | 物理护甲的 `2/3` |
| `explosion`、`electrical` | 物理护甲的 `1/2` |
| `magic` | 魔法抗性 |
| 其余类型，包括 `true` | 该函数中使用 0 抗性 |

简化的基础计算为 `floor(floor(amount + 0.5) × (1 - resistance))`。例如基础伤害 20、物理护甲 0.5，在没有其他效果时，物理伤害结算为 10，爆炸伤害结算为 15。

完整的 `Battle.damage()` 还会处理无敌、护盾、免疫、护甲变化、特殊加成、Boss 变身和死亡状态。真实伤害只说明基础抗性选择，不意味着自动绕过所有状态；部分能力会显式传入 `bypass` 等选项。近战闪避也在专门逻辑中处理。

### 6.4 投射物的表现和命中

投射物记录起点、终点、目标 ID、出生时间、命中时间、伤害类型和范围等字段。不同种类有不同规则：

| 类型 | 主要处理 |
| --- | --- |
| 普通箭矢 | 发射时结合目标运动预测和随机偏移确定落点，显示弧线 |
| 炮弹 | 面向落点飞行，命中时按范围筛选受影响单位 |
| 魔法弹 | 目标存活时更新终点，模拟逐步移动与加速 |
| 火雨 | 独立推进落点方向的运动，到达后产生伤害和效果 |
| 导弹 | 有发射阶段、速度和转向限制，按自身规则追踪目标 |
| 集束弹 | 到期后生成多个子弹，各自保留落点和命中时间 |

普通弧线的显示计算位于 [world-coordinates.ts](../apps/kr1/src/rendering/world-coordinates.ts)，在起终点插值上加入 `450 × flight² × t × (1-t)` 的纵向偏移。它是显示轨迹；伤害由 `updateProjectiles()` 决定，不通过精灵像素碰撞结算。

部分爆炸支持 `damageRange`，根据落点到目标的椭圆距离在最大伤害和最小伤害间衰减。是否打飞行单位、目标消失后如何处理，则由具体投射物分支决定。

### 6.5 持续状态与死亡

中毒、缠绕、减速、眩晕等效果保存结束时间，周期伤害另存下一次 tick 时间。它们在固定模拟步内检查，不为每个敌人创建浏览器定时器。

例如中毒检查 `poisonUntil` 与 `poisonAt`；缠绕既限制行动，也按自己的伤害节奏结算。眩晕、回血、召唤、施法等行为还存在更新优先级，不是所有状态都同时执行。

死亡处理会释放阻挡关系，记录金币和事件，并可能加入死亡爆炸、衍生单位或墓地队列。死亡实体通常保留一段时间供尸体与动画绘制，之后才从数组清理；“已死亡”与“对象已删除”是不同阶段。

## 7. 英雄、敌人能力与特殊关卡

### 7.1 英雄既有数据，也有专门行为

英雄 JSON 描述等级属性、攻击列表、技能参数、动画、召唤物、声音和贴图。大多数英雄由 [HeroController](../apps/kr1/src/simulation/heroes.ts) 驱动，Gerald 则保留在 `Battle` 中的专门逻辑。

控制器保存技能上次使用时间、延迟动作、英雄投射物、地面区域效果与表现对象。技能可以先开始动画，再通过战斗时间队列在前摇结束时执行命中或召唤。

`later()` 把动作放入队列，`cancel()` 只移除标记为施法中的动作，并处理对应冲刺状态。这意味着“移动打断技能”不是取消场上一切效果：已释放的投射物或区域效果有自己的生命周期。

英雄更新还依次考虑死亡与复活、眩晕、冲刺或变身、移动路点、动作忙碌期、经验和技能选取。技能类型中仍有按英雄 ID 和实体类型处理的分支，增加全新机制通常需要同时调整数据和逻辑。

### 7.2 经验、回血与复活

战斗行为先累积 `queuedXp`，控制器在适当的空闲阶段按难度系数结算经验，再判断升级。升级时更新等级并恢复对应生命，触发动作和成就事件。

脱战回血依赖距上次受伤的时间、回血间隔和回血量。死亡后，控制器等待复活时间和复活动画完成，再恢复战斗状态。当前存档保存选中的英雄；这些局内字段不能当作跨关卡保存的英雄成长系统。

### 7.3 敌人能力和关卡脚本

[EnemyAbilities](../apps/kr1/src/simulation/enemy-abilities.ts) 与 `Battle` 内部方法共同处理敌人的特殊行为。敌人状态中包含远程攻击、范围打击、召唤、护盾、回血、变身等字段，能力按照当前时间和阶段推进。

关卡级事件还有独立模块，例如 [point-spawner.ts](../apps/kr1/src/simulation/point-spawner.ts) 的定点刷怪、[props.ts](../apps/kr1/src/simulation/props.ts) 的场景道具，以及 [dark-tower.ts](../apps/kr1/src/levels/scripts/dark-tower.ts) 的关卡脚本。战斗层负责把它们的状态和待生成单位纳入全局流程。

### 7.4 无尽模式怎样继续生成波次

[EndlessWaves](../apps/kr1/src/simulation/endless-waves.ts) 根据配置、当前难度阶段和随机数生成后续波次，包括入口组合、敌人组与 Boss 波。阶段在十波节点推进，敌人属性通过成长规则计算。

[Endless](../apps/kr1/src/simulation/endless.ts) 另外管理分数、提前开波奖励、萨满施法和图腾等机制。当前波次刷怪结束时生成后续波次，失败后记录对应关卡和难度的成绩。它不是把战役波次简单循环播放。

## 8. 坐标、相机与大屏渲染

### 8.1 三种坐标需要分清

项目同时使用战斗模拟坐标、参考界面坐标和浏览器 CSS 坐标。模拟空间以高度 768 为基准，参考界面以 1920 × 1080 为基准，浏览器窗口则可以采用其他尺寸。

[world-coordinates.ts](../apps/kr1/src/rendering/world-coordinates.ts) 定义：

```text
HEIGHT = 768
WIDTH = 768 × 16 / 9
OFFSET = (WIDTH - 1024) / 2
factor = 1080 / 768

reference.x = (world.x + OFFSET) × factor
reference.y = (768 - world.y) × factor
```

横向偏移把以 1024 宽为基准的内容放入宽屏参考空间；纵向翻转处理模拟坐标与屏幕向下为正的差异。反向函数用于把参考点还原到模拟空间。

点击战场时，还需撤销浏览器布局缩放和相机变换。绘制世界位置上的提示时，则沿相反方向投影到 HUD。直接把 `clientX/clientY` 当作敌人或英雄坐标，会在缩放后产生偏差。

### 8.2 大屏适配不只是放大 Canvas

[display-layout.ts](../packages/game-web/src/display-layout.ts) 计算 CSS 缩放、逻辑大小和视口；`Scene` 监听容器尺寸变化，并在渲染时检查设备像素比变化。

显示模式决定内容如何放入视口：原始比例模式保留居中的 16:9 区域，其他模式结合世界边界与安全区域计算画面。`auto` 模式的相机初始比例同时考虑覆盖视口和安全区域可见性。

渲染质量与相机缩放是两个维度。质量决定 Canvas 像素密度，预设按像素预算计算分辨率；原生质量考虑设备像素比，并限制总像素预算到 3840 × 2160。窗口比例不同时，某个质量档并不意味着输出尺寸必须恰好等于该档常见的宽高。

### 8.3 相机围绕操作点缩放

[GameCamera](../packages/game-web/src/camera.ts) 保存视口、世界边界、缩放和偏移，提供 `project`、`unproject`、`pan`、`zoomAt`。

`zoomAt` 尽量保持手势锚点对应的世界位置，双指操作还传入新中心，因此可以同时平移和缩放。相机会约束可见区域，地图与战场采用不同的最大缩放设置。HUD 在独立容器中布局，金币、生命、技能按钮不会像战场单位一样随相机移动。

### 8.4 图集、序列帧与前后遮挡

[textures.ts](../packages/asset-runtime/src/textures.ts) 从共享图片源构造图集帧纹理，保留帧矩形、原始尺寸和裁剪偏移。这样不同动画帧即使透明边缘被裁掉，也能按统一锚点定位。

`animationFrame()` 根据年龄、帧区间或显式 `sequence` 取帧；循环动画取模，非循环动画停在末帧。移动方向、攻击阶段等由模拟状态决定，渲染层据此选择动画和朝向。

`Scene` 为不同层设置绘制深度，普通单位还按纵向位置计算 `zIndex`，让靠近画面下方的单位覆盖后方单位。特效、地面图像和 UI 使用各自的层级规则。

### 8.5 对象怎样复用

场景使用字符串键映射到 `Sprite`。一次绘制中，被使用的精灵标记为可见；未再被使用的精灵会被销毁并从映射移除。这个机制复用存续实体的显示对象，但不是跨实体统一的对象池。

血条采用另一种方式：按需要扩充数组，未使用的条目隐藏，切换关卡时清理。纹理与资源包则由 Map 和 Promise 复用，不随每个死亡单位销毁。

## 9. 界面、文本与输入

### 9.1 JSON 界面树如何落到 Pixi

[GameView](../packages/game-web/src/ui-tree.ts) 根据界面数据递归创建容器、图片、背景和子视图，设置位置、旋转、缩放、锚点与透明度。应用层再绑定按钮动作和具体游戏状态。

文本通过 Canvas 2D 绘制成纹理，使用数据中的字体指标、基线、阴影与对齐配置。自动换行会区分拉丁词组与中日韩字符；若数据提供 `source_lines`，则使用已有分行。相同文本不会重复重建，显示像素密度变化时会刷新文本纹理。

### 9.2 点击选中谁

[picking.ts](../apps/kr1/src/interaction/picking.ts) 使用单位和对象的命中矩形，而非逐像素读取贴图透明度。英雄、敌人、士兵、防御塔和道具有各自的区域数据。

多个对象重叠时，候选按层级和纵向位置排序，取第一个结果。点击图像的透明边缘是否生效，取决于命中区域；它不一定严格等于可见像素边界。

### 9.3 点击、拖动和缩放怎样区分

`main.ts` 保存当前指针集合、拖动起点、上一位置及命中的单位。移动超过阈值后，才进入拖动状态：拖空白处移动相机；拖英雄发出移动指令；拖兵营士兵则操作该塔的集结点。

士兵拖动记录所属塔 ID，因此指令归属集结点，而不完全依赖最初被抓住的士兵实例。松开后，主程序调用 `rally()`、`moveHero()` 或 `moveSoldier()`，再根据结果显示落点反馈。

滚轮按指数系数改变缩放，双指按两点距离比改变缩放，并结合中心点移动。暂停、弹窗、技能瞄准和 HUD 区域等状态会影响相机手势是否允许，避免同一次操作同时改变视角和施放技能。

## 10. 音乐与战斗音效

[AudioRuntime](../packages/audio/src/index.ts) 使用 `AudioContext`。音频按 URL 缓存解码 Promise，再将声音键映射到 `AudioBuffer`；播放时创建新的 `AudioBufferSourceNode`，复用已经解码的音频数据。

音乐与音效连接到独立的 `GainNode`，可分别调节音量。音乐切换会停止旧音源并开始新音源；首次指针操作用于恢复浏览器可能挂起的音频上下文。

[CombatCues](../apps/kr1/src/audio/combat-cues.ts) 将战斗中的语义音效映射为具体文件，并处理：

- 顺序或随机选择音效变体，以及音量区间。
- `ignore` 时间窗口，抑制短时间重复请求。
- 声源分组和最大同时播放数；达到上限时停止预计最早结束的同组声源。

顺序音效即使本次被 `ignore` 窗口抑制，也会推进序号。这个细节决定下一次实际播放哪个变体，不能简单理解成“播放成功后才切到下一段”。

## 11. 本地存档与成长进度

### 11.1 键名隔离

[createStorageKeys](../packages/game-storage/src/index.ts) 使用游戏 ID、版本和槽位组合键名。当前进度键形如：

```text
kingdom-rush:kr1:v1:slot:1:level:1:progress
```

设置使用 `kingdom-rush:kr1:v1:settings:<field>`，不放在某个存档槽内。浏览器 `localStorage` 按站点来源隔离，URL 路径本身不能隔离数据，因此需要显式前缀。

仓库在 GitHub 上改名为 `kingdomRush` 不会自动改变这里的游戏 ID、基础路径或存档版本。它们由 [games.config.ts](../games.config.ts) 配置。

### 11.2 不同进度分别存什么

| 内容 | 保存规则 |
| --- | --- |
| 战役进度 | 每关保存最高星数与通关次数，再次低星通关不会降低已有星数 |
| 英雄／钢铁挑战 | 分别保存已完成的最高难度 |
| 总星星 | 汇总战役星数，每项已完成挑战额外计一颗星 |
| 星星升级 | 保存各类别等级，已花费星星根据升级表价格重新计算 |
| 成就 | 保存累计计数和已获得 ID；部分计数仅在当前关卡内有效 |
| 无尽成绩 | 按关卡与难度保存更高分数及那次对应的波数 |
| 英雄选择 | 保存所选英雄 ID |
| 全关卡解锁 | 单独保存解锁标记，不伪造通关星数 |

成就由实际观察到的战斗事件推进，不会凭历史存档推算未记录的事件。胜利保存由主程序在结束状态首次出现时处理，避免每次渲染都重复增加通关次数。

当前没有服务器存档、账号同步或局中战场快照恢复。版本号提供命名空间，但并不代表已经实现旧存档迁移；JSON 读取也没有完整的损坏存档修复流程。

## 12. 构建、离线缓存与更新

### 12.1 构建产物

`pnpm build` 执行 TypeScript 检查与 Vite 构建，输出到 `dist/kr1/`。应用基础路径是 `/kr1/`，部署位置需与其匹配。仓库名与网页部署路径是独立概念。

[resource-sizes.ts](../tools/build/resource-sizes.ts) 生成资源大小信息；[pwa.ts](../tools/build/pwa.ts) 读取输出文件和 Worker 源码，为资源内容计算发布版本，并生成 `sw.js`。

发布哈希包含游戏 ID、基础路径、Worker 源码、输出文件路径和内容。即使静态资源 URL 不变，只要发布内容变化，生成的缓存版本也会变化。

### 12.2 启动缓存与按需缓存

[pwa-worker.ts](../packages/asset-runtime/src/pwa-worker.ts) 在安装阶段缓存启动需要的 HTML、脚本、样式、标题资源、字体和图标等内容。完整关卡和英雄资源在访问时缓存。

受管理的资源请求先查当前版本缓存，未命中再读取网络，并将成功响应写入缓存。访问应用基础路径的导航请求使用缓存的 `index.html`。

所以 PWA 安装完成不表示全部关卡都已经可离线游玩。离线前需要访问目标关卡并加载所用英雄；换版本后也不能假定旧版本下载过的所有内容都已经出现在新缓存中。

### 12.3 更新为什么不会立刻替换战场

新 Worker 下载完成后保留浏览器的 waiting 生命周期。客户端展示更新状态，玩家选择更新时才发送 `APPLY_UPDATE`，Worker 调用 `skipWaiting()`，客户端在控制器切换后重新加载。

新版本激活时删除同一游戏前缀下的旧版本缓存。客户端初始化还会等待正确的 Worker 接管，确保首次进入游戏的资源请求也能参与按需缓存。

该能力只在生产版本启用。缓存内容与 `localStorage` 存档是不同存储：更新资源缓存的流程不等于迁移或备份玩家进度。

## 13. 性能处理与当前边界

当前代码中已经使用的处理包括资源按需加载、加载 Promise 复用、图集共享、存续精灵复用、血条复用、文本内容变化时才重建，以及渲染像素预算限制。

性能栏提供帧间隔观察；开发／测试条件下，`main.ts` 还暴露手动时间控制、画面状态与性能采样入口，采样记录包含更新耗时、渲染耗时和敌人数。它们是排查与复现工具，不能直接代表所有设备上的性能结论。

理解以下边界有助于准确判断代码：

- **固定步长没有追帧数量上限。** 较长帧间隔可能触发很多次模拟更新，当前主循环没有按最大步数截断积压时间。
- **目标查询主要扫描数组。** 多个塔和技能会反复过滤敌人并排序，当前没有统一空间索引。
- **A* 使用线性开放列表。** 实现便于理解，但不应据此宣称已经适合极大网格或大规模同时寻路。
- **资源包在页面会话内保留。** 当前未见按内存预算淘汰关卡和英雄包的机制；访问更多内容会增加驻留资源。
- **固定步长不等于全场景渲染插值。** 普通单位主要显示最新模拟状态，特定弹道等有各自的轨迹计算。
- **数据驱动存在边界。** 英雄、Boss 和特殊塔包含专门分支；添加新的机制需要理解模拟与显示两侧。
- **生成数据已随仓库提供。** 不应把现有构建命令描述为可以从原作工程重新生成全部美术和玩法数据。

以上描述用于解释现状，不是本次文档变更新增的行为，也不是已经实施的优化计划。
